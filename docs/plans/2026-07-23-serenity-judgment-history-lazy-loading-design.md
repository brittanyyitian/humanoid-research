# Serenity 复盘历史按需加载设计

## 目标

在不改变每日复盘内容、判断历史和相对观察池算法的前提下，将全部股票的完整判断历史移出股票雷达首屏。

当前 `serenity_judgments.json` 约 464 KB，包含 60 支股票的完整历史快照。首屏横向比较只需要每支股票的首次判断价格和所属市场，右侧详情才需要当前股票的完整快照、最新判断价、判断变化和触发条件。

成功标准：

- 完整 `serenity_judgments.json` 保持不变。
- 判断后涨跌、相对观察池、最大回撤和判断变化记录保持一致。
- 当前股票的复盘历史按需加载并缓存。
- 复盘加载失败不阻断股票主体分析，用户可以重试。
- 生成详情与完整判断集合逐项一致。

## 方案

采用“轻量基线索引 + 逐股票完整历史”：

- `serenity_judgment_index.json` 保存集合元数据，以及每支股票的 `entityId`、首次判断价格和市场。
- `serenity_judgment_details/<entityId>.json` 保存完整判断历史对象。

不把复盘历史合并进股票分析详情文件，因为两者来自不同数据合同，独立投影更容易验证和回滚。

## 前端数据流

股票雷达静态读取基线索引，用于计算观察池的平均判断后涨跌。选中股票时，并行加载：

1. 股票完整分析详情。
2. 该股票完整复盘历史。

股票分析详情加载成功后立即展示，不等待复盘历史。复盘区域在历史加载期间显示“正在加载每日复盘”，失败时显示重试入口。成功后写入会话内缓存，切回该股票不再重复加载。

复盘算法改为显式接收基线索引映射，不再依赖全局完整历史映射。当前股票的判断后涨跌、最大回撤和时间线仍使用完整历史对象计算。

## 生成与验证

`generate-dashboard.mjs` 每次生成时清理并重建复盘详情目录，避免已移除股票留下陈旧文件。

测试覆盖：

- 基线必须来自排序后的首个有效快照；没有快照时回退到 `latest`。
- 投影不得修改完整历史。
- 每个详情文件必须与完整集合中的对应行完全一致。
- 数据校验、生产构建和浏览器回归均通过。
